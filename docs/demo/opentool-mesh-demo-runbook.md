# OpenTool Mesh Demo Runbook

This runbook is the source of truth for running the current repository demo.

## 1. Goal

Show a complete OpenTool Mesh loop:

```text
publish -> discover -> resolve -> verify -> call -> trace -> report -> dashboard
```

The demo uses a Solidity static-analysis capability, a sample tool node, an audit-agent example, local runtime storage, and a read-only dashboard.

```bash
corepack pnpm demo:publish
```

Expected result:

- Manifest JSON is written to local 0G-style storage.
- ENS-style records are updated.
- The capability index includes `solidity-static-analysis`.

### 5.4 Discover, Resolve, Verify, Call, Trace, Report

```bash
corepack pnpm demo:audit-agent
```

Or use the all-in-one command:

```bash
corepack pnpm demo:run
```

`demo:run` reuses an already running tool node when possible and avoids port conflicts with `demo:tool-node`.

### 5.5 Service Health Check

```bash
corepack pnpm demo:health
```

Expected results:

- Dashboard health returns `200`.
- Tool-node health returns `200`.

Health checks only prove that processes are alive. They do not prove that the dashboard displays the latest runtime data.

### 5.6 Runtime Product Inventory and Health-Check Scope

`/opt/wanman/products.json` is an external operations inventory. It is not generated by this repository.

The only services directly proven by this repository are:

- Dashboard: `http://127.0.0.1:3000/`, health `http://127.0.0.1:3000/api/health`
- Tool node: `http://127.0.0.1:4318/health`, invocation `http://127.0.0.1:4318/invokeTool`

If an operations script expects `/opt/wanman/products.json`, that file must be generated by deployment/bootstrap tooling outside this repository. A missing inventory should be reported as `unknown:no_product_inventory`, not as full product health.

A temporary minimal inventory can include only the repository-proven services and should include `generatedAt` and `source` fields.

## 6. Dashboard Alignment Rules

The dashboard follows one authoritative selection rule:

1. If `.opentoolmesh/storage/traces/*.json` contains successful traces, choose the latest successful trace by `storage.persistedAt`.
2. Use only data bound to that trace:
   - Tool output artifact from the trace's `tool-output` artifact.
   - Audit report from the trace's `audit-report` artifact.
   - Manifest from `trace.tool.manifestUri`.
3. If no successful runtime trace exists, fall back to the fixture baseline as a complete set.
4. Do not mix runtime trace data with fixture report, artifact, or manifest data.

Fixture baseline files:

- `examples/audit-agent/fixtures/sample-execution-trace.json`
- `examples/audit-agent/fixtures/sample-tool-output.json`
- `examples/audit-agent/fixtures/sample-report.json`
- `services/tool-node/manifests/solidity-pattern-scanner.manifest.json`

Runtime sample IDs should be treated as live data, not fixed documentation constants.

## 6.1 Closed-Loop Field Checklist

Check these fields across CLI output, trace, report, manifest, and dashboard:

- Trace ID
- Trace URI
- Report ID
- Report URI
- Manifest URI
- Requested capability
- Tool identity
- Peer ID
- AXL method
- Tool-output artifact URI/hash
- Audit-report artifact URI/hash

Required relationships:

- `trace.tool.manifestUri` equals the manifest `storage.manifestUri`.
- `trace.tool.manifestHash` equals the manifest `integrity.manifestHash`.
- `trace.invocation.peerId` equals the manifest `invocation.axlPeerId`.
- `trace.invocation.method` equals the manifest `invocation.axlMethod`.
- `report.reportId` matches the report artifact selected from the trace.
- Every `report.findings[].traceId` equals the current trace ID.
- Every `report.findings[].toolId` equals the current trace tool ID.

Recommended order:

1. Run `corepack pnpm demo:run`.
2. Inspect the latest successful runtime trace.
3. Open the dashboard and confirm displayed fields match that trace.
4. If the dashboard falls back to fixtures, verify that no valid successful runtime trace exists.

## 7. Demo Talk Track

- "The agent asks for a capability, not a hard-coded endpoint."
- "Before invocation, the SDK verifies ENS-style identity and the manifest."
- "Execution happens in a separate remote tool-node process, not as a local in-agent function."
- "Trace, artifact, and report evidence is written to local 0G-style storage for provenance review."

## 8. Acceptance Mapping

| Acceptance item | How to prove it in the repository |
| --- | --- |
| Tool can be published | `corepack pnpm demo:publish` prints manifest fields and writes runtime state. |
| Agent can discover a tool | `corepack pnpm demo:run` prints discovery output. |
| Manifest can be verified | `corepack pnpm demo:run` prints `verify.ok=true` and checks. |
| Agent can remotely invoke the tool node | Run `demo:tool-node` and `demo:run`, or use the all-in-one demo command. |
| Trace is persisted | `demo:run` prints the trace file path. |
| Report references trace | Runtime report and fixture report include `traceId`. |
| Dashboard fields align | `apps/dashboard/lib/demo-run.ts` selects the latest successful runtime trace before fixture fallback. |
